# 窮鬼勇者：全面改版盤點與提案

盤點日期：2026-09-06。程式基準：`codex/storybook-collection-overhaul` 的 `13d9963`，另有使用者原先未提交的樣式與素材工作。此次是程式、規格與本機首頁檢視，沒有驗證正式 Firebase 權限或 Cloudflare 線上環境。

本文件的「現況」可由程式確認；「建議」與數值範例尚未實作。使用者已確認方向是有收集樂趣的記帳遊戲、每日冒險與成長、統一畫風、真正換衣服／配件，並允許不沿用原架構。

## 結論與取捨

需要重整產品結構，但不需要連 React、Git、Cloudflare 和已可靠的記帳存檔一起推倒。現在的主要矛盾是：記帳金額同時扮演財務資料與攻擊力；月曆被叫作冒險地圖；任務靠造訪頁面湊進度；收藏分散在商店、造型、手帳和兩套人物系統中。單純換背景和增加影片，無法解決這些問題。

建議定位為「用真實記帳推進的輕冒險換裝遊戲」。每天可以只花十幾秒記帳，也能多玩一小段冒險；角色、夥伴和自己的小庭院是長期收集目標。

| 路線 | 優點 | 代價 | 判斷 |
|---|---|---|---|
| 延續金額打怪，整理現有頁面 | 改動少、最快延用素材 | 金額與戰力矛盾、月曆冒險和整人影片產能問題仍在 | 適合短期維護，無法完成這次核心目標 |
| 記帳＋短篇冒險＋自由換裝 | 保留戰鬥、地圖、任務，又能把收集串成目標 | 要改進度模型，先證明分層角色可行 | **建議採用** |
| 純庭院養成與換裝 | 記帳負擔最低，美術展示集中 | 戰鬥和探索感較弱，裝飾內容需求高 | 可作後續庭院擴充，不必現在取代冒險 |

## 新的記帳與冒險循環

**如實記帳／確認零消費 → 今日冒險準備完成 → 選擇短路線 → 短戰鬥或事件 → 取得收藏進度 → 穿上並展示。**

記帳提交成功就先顯示明細與可回復的操作結果；角色短回饋不能擋住繼續記帳。想玩的人點「繼續冒險」，只想記帳的人可以立即離開。戰鬥畫面不再是輸入一筆帳的必經入口。

### 記帳與預算

- 單一帳本統一支出、收入與轉帳語意；第一期先合併目前主帳本與公會流水，再依需求補帳戶／轉帳。轉帳不可重複算收入或支出。
- 金額以最小貨幣單位整數保存，保留幣別、分類、交易日期、建立時間、修訂版本。先維持單一主要幣別，不提前加入匯率系統。
- 常用分類、上次輸入、快速金額和計算機維持一手可用；明細、修改、刪除、補登都走相同可靠流程。
- 每日額度可保留為個人預算工具；增加月度／固定支出視角，避免用單日超支判定一個人的遊戲表現。統計明確標示支出、剩餘及超出數值。
- 零消費是使用者確認，不是系統把沒有紀錄當成零。稍後新增真實支出自動取消零消費狀態。
- 補登改善帳本完整度；不追發每一個漏掉日期的日常貨幣。永久旅程也不因漏記卡死。

### 冒險與戰鬥

- 第一個版本只做每日一段短旅程，不新增可以付費補充、可以囤積的體力貨幣。當日首次記錄或零消費確認取得一次準備資格；分十筆、提高金額都不多給。
- 冒險由章節難度、角色成長和所選夥伴技能決定，不讀取本筆消費金額。外觀部件不綁戰力，喜歡的衣服可以一直穿。
- 每段有一個清楚選擇，例如「圖書館小徑：服飾線索」或「森林岔路：夥伴故事」。獎勵總價值相近，選擇改變收藏方向，不製造必選最優路線。
- 短戰鬥提供蓄勢、施法、命中、回復與敵方反應；點一下夥伴技能即可參與。可開快速結算／減少動態，結果與完整播放一致，不靠連點技巧決定記帳收益。
- 每日準備資格可以稍後使用；不以半夜到期造成追趕。試作先允許保留最近 3 次未完成旅程，超出後只累積永久足跡，不堆待辦。這是待驗證上限。
- 帳本可隨時修正。已領的一次性日常獎勵保留歷史取得事件，當日不再重領；不要為了防刷鎖住真實帳目，也不要刪帳後讓怪物復活。遊戲能限制重複收益，無法驗證現實是否真的消費。

### 地圖、任務與成長

- 地圖改成永久章節，例如「學院庭院 → 市集小路 → 書頁森林」，區域包含事件、角色與可預覽的收藏。跨月不重置主線。
- 帳本月曆、收支統計、補登留在手帳的「帳本」頁；地圖節點不再兼任某月某日。
- 任務自動追蹤：當日記錄／確認、每週回顧、累積 3／7／14 個記錄日、完成某章節、收齊某系列。移除單純打開頁面的任務。
- 每日回顧只檢查當日內容，修改後提示「有更新可回顧」，已發獎勵不再重發。任務回饋集中，避免每條都要去不同頁點領取。
- 成長有實際用途：解鎖章節、夥伴行為、房間擺設和穿搭展示。等級數字只輔助呈現，不以升級本身填充內容。
- 連續天數可以展示，主要里程碑使用累積日；回來的玩家從原處繼續，不清空長期收藏進度。

## 收藏與貨幣

每個可收藏物件都必須回答：長什麼樣、能放在哪、如何取得、還差多少、取得後在哪裡用。衣服、髮型、帽子、手持物、夥伴、庭院小物要能在遊戲裡看得見；不要讓收集主要變成稱號清單或只在商品卡有效的特效。

- 「收藏」統合衣櫃、圖鑑與小店。查看未取得物件能試穿、標記心願、直接看取得條件；領到後直接穿上或邀請夥伴。
- 新玩家直接有一小組可混搭的免費部件，第一天就能改出自己的樣子；不能等一星期才體驗第一次換裝。
- 建議節奏：第 1 天第一次混搭；累積 3 天第一位夥伴；7 天可自選一件配件；14 天一組主題穿搭或庭院物件。這是內容投放草案，尚未完成對應素材。
- 套裝依系列收集，每件有獨立用途；收齊可以給展示姿勢／小故事，避免只把同一張整人圖換色當作多件內容。
- 維持黃星作日常兌換、紫星作較慢的紀念兌換。首頁優先顯示黃星，完整錢包放小店；不用把四種資源永久擠在角色上方。
- 第一階段以確定兌換為主；既有普通券／金券與收藏保留，提供清楚的舊票入口。新扭蛋池若要擴充，先定保底、重複補償、可直接兌換的替代途徑，不先賣抽獎期待再補內容。

經濟試算草案：記錄日 2 黃星＋可選回顧 1 黃星，每週累積 5 天加 5 黃星。每週 5 天且有回顧約 20 黃星，7 天且有回顧約 26 黃星；基本配件 6、主要衣服 18、較完整套組 36，可形成短、中期目標。紫星來自週／章節里程碑，稀有物件約 2–4 枚。正式採用前模擬 7／30／90 日玩家、不做回顧玩家與既有高餘額玩家，避免單看新帳號。

這套數字若採用，必須**取代**舊日結算、手帳禮、商店簽到等重疊黃星來源，不能把新獎勵繼續疊上去。既有餘額不縮水、已購物件不撤回；任何舊券轉換另訂對應表，不自動猜比例。

## 首頁、手帳與導覽

建議底部固定五個入口：**首頁｜冒險｜＋記帳｜手帳｜收藏**。

| 入口 | 第一眼看見 | 收納內容 |
|---|---|---|
| 首頁 | 自己的角色與夥伴、下一個目標、今日記錄狀態 | 簡短收支摘要、今日手帳捷徑、繼續冒險；頭像只進個人資料與設定 |
| 冒險 | 當前章節、下一節點與本段獎勵 | 永久地圖、事件、戰鬥、夥伴能力 |
| ＋記帳 | 金額、分類、日期；儲存即完成 | 全域快速面板，從哪頁開就回哪頁；不強制載入戰鬥場景 |
| 手帳 | 今日一頁，明確記錄狀態 | 今日／帳本／目標。帳本含明細、月曆、統計；目標含週任務與成長 |
| 收藏 | 大型目前搭配預覽、心願進度 | 衣櫃／圖鑑／小店；減少到設定頁找衣服 |

首頁的手帳捷徑有圖像也有文字：「今日手帳 · 已記錄／待回顧」，點擊區保持容易觸及。完成後改成可閱讀的紀錄，不讓入口消失；只在真的有新收藏或待領獎勵時提示。頭像不是手帳的必要入口，也不靠一直跳紅點提醒。

首頁不以大面板覆蓋角色，但也不再為保留舊 HUD 的絕對位置犧牲資訊。財務數字清楚、人物完整落地、導覽易按三者一起驗收。手帳可以有翻頁與書籤的視覺語言，日期／金額／任務仍用正常可讀的文字和清楚分類。

新手首段流程：選名字與基礎外觀 → 直接獲得免費混搭選擇 → 看到「記一筆／今天零消費／稍後」 → 儲存後有角色回饋與可選冒險 → 展示第一個收藏目標。不要求製造一筆假消費才能通過教學，也不連續介紹全部貨幣與功能。

## 人物為什麼還像一體，怎麼改

這個觀察正確。薄荷與晚星的臉、頭髮、帽子、衣服、手和帳本都已畫在整個角色動畫裡；目前切換的是這張整體動畫。兩件衣服加一隻獨立夥伴，只是初步的造型選擇，不能宣稱完整自由換裝已做完。

新版應先製作**可拆的角色母版和部件規格**，再擴充商品：

- 身體、臉、前／後髮、上衣、下身、鞋、帽、手持物、背飾各有固定支點、比例與遮擋順序；夥伴獨立。
- 一件衣服可能由軀幹、左右袖等多張部件構成；角色抬手時袖子跟手臂動，不把衣服當貼紙覆在一段整人影片上。
- 同一套待機、招呼、施法、勝利動作套用目前搭配，商店試穿與首頁／戰鬥引用同一份外觀資料。
- 保留目前溫暖霧面水粉、奶油／薄荷／靛紫的方向；背景減少高密度細節，讓輪廓和動作清楚。頭身、描邊、光源、材質、表情表與色板一起固定。
- 原角色分層需要補畫被遮住的身體、頭髮和衣服，不能只把現有合成圖自動裁成幾片就當正式素材。自由混搭也需要長髮／帽子、斗篷／背飾、手持／手勢的相容性規則。

技術選擇建議：React 保留表單與導覽，角色及冒險場景使用獨立 2D 渲染層。優先評估 PixiJS 搭配共用骨架；若採用 Spine，官方 skins 支援把不同物件的 attachments 組合到同一骨架，不必預先輸出每一種完整搭配。Spine 有正式 PixiJS runtime；需確認編輯器／runtime 授權及素材製作環境，再決定正式導入。參考：[Runtime Skins](https://esotericsoftware.com/spine-runtime-skins)、[spine-pixi](https://esotericsoftware.com/spine-pixi)。

較簡單的 React 分層剪紙動畫可以作技術試作：投入較低、能直接驗證槽位，但複雜關節、布料、前後轉向較難維護。PixiJS 本身提供場景物件與渲染，不會自動產生角色骨架或修好素材；這些仍需要製作。參考：[PixiJS Scene Objects](https://pixijs.com/8.x/guides/components/scene-objects)。現在沒有因這份提案安裝付費工具或替換整個框架。

**先做一個可驗收的試作：同一角色、2 髮型×2 上衣×2 下身×2 帽飾＝16 種搭配，共用待機／招呼／施法 3 組動作。** 檢查袖子跟隨、長髮遮擋、腳底穩定、換裝不改臉、商店與首頁一致；16 種都成立後才批量做衣服。不先生成 16×3 支整人物影片來假裝完成。

## 底層與開發環境

建議分成五個責任清楚的模組，逐步抽離，不要求一次重寫全部檔案：

1. **帳本**：交易明細是收支事實來源；日／月摘要可重算。新增、修改、刪除、補登共用提交介面。
2. **冒險**：記錄日資格、旅程、章節、戰鬥結果；與金額分開，存檔後產生一次性進度事件。
3. **獎勵與錢包**：每次取得／消耗有穩定 operation ID、來源、規則版本、變動明細；領取與餘額一起提交。畫面不能自行寫一份餘額。
4. **物品與角色**：統一 item ID、來源、價格、槽位、相容性、資產版本、持有與裝備狀態；首頁、衣櫃、商店共用。
5. **儲存與同步**：本機／Firebase 實作同一契約；區分「此裝置已存」「等待同步」「雲端已存」。服務工作者快取不等於帳本離線同步。

不因使用 Cloudflare 就立刻從 Firebase 搬到另一套資料庫。先保留 Cloudflare Pages 前端部署與現有身分／資料儲存，補完整存檔契約、備份匯入、訪客綁定與權限測試；若確定要排行榜、可交易道具或付費經濟，再把權威獎勵計算移到受信任服務。現有客戶端交易能防一般重複提交，不能當作完整反作弊系統。

環境工作包括：schemaVersion 與可重試遷移、匯出後再升級、雙裝置衝突處理、明確時區、錯誤／同步狀態、測試存檔隔離、主要流程整合測試、動畫按需載入和離屏停止。正式驗收包含 iPhone Safari／standalone PWA、窄螢幕與大字設定，不只桌面模擬畫面。

Git 延續工作分支；每個里程碑獨立提交可回退，Cloudflare 以預覽環境驗收後再合入 main。現在只確認倉庫 README 所記錄的 Pages 設定，未查核遠端控制台，不能宣稱正式部署或雲端同步已驗收。
